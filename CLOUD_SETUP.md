# Atlas Cloud — Supabase + Vercel

This edition keeps the Atlas homepage and workspace, adds Google sign-in with a private workspace per account (email signup remains optional), and stores research in Supabase PostgreSQL. Vercel Workflow runs research in durable stages. No Render service or Render database is required.

## 1. Create a free Supabase project

1. Sign in at https://supabase.com/dashboard and create a project on the **Free** plan.
2. Choose a region near your users (Singapore suits Bangladesh). Save the database password in your password manager.
3. Open **SQL Editor**, create a query, paste `supabase/migrations/001_atlas.sql`, and run it **once**. This creates a separate `atlas` schema and row-level ownership policies. Keep `atlas` out of Supabase's exposed Data API schemas.
4. Set up Google sign-in using **GOOGLE_SIGN_IN.md**. This flow uses Google for identity and Supabase for sessions; it does not require Brevo or signup/password-reset emails.
5. In **URL Configuration**, set Site URL to `http://localhost:3211` for local testing and allow both `http://localhost:3211/auth/callback` and `http://localhost:3211/auth/callback?**`. This query wildcard is restricted to the exact local callback path.
6. If you later enable email/password in Atlas, configure a working custom SMTP sender first. Keep email confirmation enabled and set the Supabase password minimum to 12 characters. Do not disable confirmation as a workaround for email delivery.

## 2. Connect the local cloud edition

Run `npm install` then `npm run setup`. Open `.env.local` locally; never paste secrets into chat or commit this file.

- `NEXT_PUBLIC_SUPABASE_URL`: Project URL from project API settings.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: Publishable key from API settings. This key is intentionally public; the database's ownership rules protect data.
- `DATABASE_URL`: **Transaction pooler** URI from Supabase's **Connect** dialog, usually port **6543**. Replace the password placeholder with your URL-encoded database password. Use the connection string exactly as shown for your project and region.
- `ATLAS_MASTER_KEY`: Generated by `npm run setup`. Keep the same value across deployments and back it up privately. It encrypts users' AI keys.
- `NEXT_PUBLIC_APP_URL`: `http://localhost:3211` locally, your exact HTTPS deployment origin on Vercel.
- `SUPABASE_DB_CA`: Optional override for the bundled official Supabase root CA. Newlines can be entered as `\n`. TLS certificate validation stays enabled.
- `ATLAS_AUTH_METHOD`: `google` (default), `email`, or `both`. This selects the UI; provider availability must also be configured in Supabase.
- `ATLAS_GOOGLE_AUTH_ENABLED`: Set `true` after connecting the Google provider. Until then, Atlas shows a clear setup status and disables the Google button.

`npm run preflight` checks that configuration values are present without printing them. You can run `npm run db:setup` to apply the database migration automatically instead of pasting it into SQL Editor. It preserves an existing Atlas schema and verifies the ownership-policy table count.

Start with `npm run dev -- --port 3211`. Open http://localhost:3211. The original local edition can continue on port 3210.

Continue with Google to create your private Atlas account, then add your AI key in **Providers & settings**. That key belongs only to this Atlas account. Existing local AI keys are not automatically shared or imported.

## 3. Deploy to Vercel

1. Put **this cloud edition folder** in a private Git repository and import it into Vercel as a Next.js project, or deploy this directory with the Vercel CLI. Do not upload `.env.local`, `node_modules`, `.next`, test data, or your old SQLite database.
2. Choose **Node.js 24**. The build command is `npm run build`; output settings can stay at Next.js defaults. `vercel.json` selects Tokyo (`hnd1`) to match this Supabase project; change it if your Supabase region is different.
3. Add the same environment variables from step 2 in Vercel's project settings. Put secrets only in variables **without** `NEXT_PUBLIC_`. Use the real Vercel origin for `NEXT_PUBLIC_APP_URL`.
4. Deploy. The included Workflow integration generates its internal routes and queue configuration. No browser tab, cron, or Render worker is needed to keep a research run going. Leave `/.well-known/workflow/` outside authentication proxy matching.
5. In Supabase Auth URL Configuration, set Site URL to your deployment origin and allow `https://YOUR-DEPLOYMENT/auth/callback` and `https://YOUR-DEPLOYMENT/auth/callback?**`. Keep localhost if you still need local development. Add preview callback URLs deliberately; avoid broad production wildcard redirects.
6. Redeploy after changing public environment variables. Vercel embeds them at build time.

Use separate Supabase projects for staging and production when possible. The supplied schema migration must be applied before opening the app.

## 4. Final live checks

- Sign in with two different Google accounts and verify return visits open the same workspace. If email login is enabled, also verify confirmation and password-reset delivery.
- Create different research projects in each. Verify their lists, search results, files, approvals, provider keys, and history remain separate.
- Add and test a provider in account A, then run a small research task. Close the browser and reopen it; the run should advance through saved stages.
- Pause a run, resume it, approve an uncertain item, and search for it.
- Sign out and verify `/workspace` asks for sign-in and private API routes reject the request.
- Use **Export data** to keep a private copy of your research. This export excludes API credentials and is a portable archive; there is no JSON re-import UI in this version.

The automated tests exercise the actual PostgreSQL schema and research engine with PGlite and mock model responses. They do not substitute for live Supabase Auth, SMTP, Vercel queue, or real-provider testing.

## Existing local research

An optional importer preserves projects, folders, research, approvals, decisions, search records, notifications, and history from the local SQLite edition. It never imports API credentials.

Create an Atlas account and obtain its UUID in Supabase Authentication → Users. Import **before that account first opens the workspace**, since workspace opening creates a starter project.

```bash
ATLAS_IMPORT_OWNER_ID=YOUR_AUTH_USER_UUID npm run import:local -- /absolute/path/to/old-project/data/atlas.db
```

This previews record counts. After checking the destination, append `--apply`. The importer refuses an account that already has projects and writes the import in one transaction. Imported findings remain available in the database; Markdown mirrors are refreshed when items are subsequently processed or approved. Re-enter your provider key in the vault after import.

## Free-plan boundaries

Supabase Free currently includes a 500 MB database and can pause inactive projects. It does not include automatic database backups. Export and back up important work independently. Free limits are not an uptime guarantee.

Vercel Hobby is for personal, non-commercial use. A business deployment for your boss may require Vercel Pro even while Supabase remains Free. Workflow, function, and AI-provider usage have their own limits or charges. This project does not enable a paid plan or purchase anything.

## Recovery and limitations

Each model call has a maximum 90-second request timeout. Evidence, synthesis, repaired output, and the final result are saved between invocations. If a worker stops after a provider charged for a response but before that response was saved, that unfinished call may need to run again; exactly-once provider billing cannot be guaranteed.

If dispatch fails, a failed session remains visible for Resume. If a job has not advanced for 10 minutes, opening State or History marks it interrupted and surfaces a notification. Completed stages remain in Supabase. There is no realtime email/push notification service in this version; notifications appear inside Atlas.

Cloud providers must use HTTPS origins from hosted presets or the administrator's `ATLAS_ALLOWED_PROVIDER_ORIGINS`. Redirects are rejected. Local Ollama/LM Studio endpoints remain available in your original local edition; Vercel cannot reach a visitor's localhost.
